# Semantic TextNavigator — Contract Checker

смотреть ветку feat
https://github.com/kam1k88/stereosagent/tree/feat/contract-intelligence-mvp

## Запуск

Требуются Python 3.10+ и (для чата) локальная Ollama.

~~~powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt

# В отдельном терминале Ollama:
ollama pull qwen2.5:7b

# Запуск:
$env:OLLAMA_HOST="http://127.0.0.1:11500"
$env:OLLAMA_MODEL="qwen2.5:7b"
streamlit run app.py
~~~

По умолчанию используется демонстрационный набор в documents/. Можно загрузить собственные TXT: тип документа и номер договора определяются по содержимому, а не по имени файла. Без Ollama доступны обзор, источники и четыре быстрые проверки; чат требует локальную модель.

## Пользователь и сценарий

Основной пользователь — специалист по закупкам, которому нужно быстро сверить сумму и срок поставки по комплекту договорных документов. Загрузить TXT → проверить итоговую таблицу → раскрыть источник → задать вопрос в чате. LLM выбирает инструменты, но факты получает только из них. Для оценки отсутствующей цены есть отдельная генерация гипотетических сценариев в структурированном JSON с выбором пользователя; она не меняет договорные факты.

## Архитектура

Streamlit Chat → собственный Local Agent Runtime → Ollama /api/chat (native tool calling) → семь allowlisted Python Tools → Domain Workflows → Evidence + Contract Snapshot. Hermes/MCP не используются: runtime и registry инструментов принадлежат приложению.

Обработка документа: ingestion/normalization → classification → extraction → evidence. Resolver применяет версионируемые правила из config/rules.json. LLM не определяет юридическую применимость изменений. MCP/Hermes, vector DB и платные API не требуются.

## Ключевые решения и компромиссы

1. **Детерминированный resolver.** Подписанное обеими сторонами допсоглашение применяется только при известных датах подписания и вступления в силу, если обе даты не позже даты проверки. Проекты и письма показываются отдельно. Компромисс: неизвестный или сложный юридический статус требует ручной проверки.
2. **Evidence-first.** Каждое найденное поле несёт файл, цитату, номер абзаца и anchor. Компромисс: точность зависит от формулировок TXT; неизвестные шаблоны требуют расширения extractor.
3. **Собственный ограниченный agent runtime.** Ollama выбирает один из семи allowlisted tools; максимум пять шагов на вопрос. Компромисс: качество tool calling зависит от выбранной модели. Чат не считается источником фактов без вызова инструмента.

## Допущения и границы

- Дата проверки по умолчанию — 10.03.2026, её можно изменить в интерфейсе.
- Подписание подтверждается явным маркером «подписано обеими сторонами»; дата вступления в силу извлекается отдельно.
- Стоимость извлекается только из контекста общей стоимости; аванс и внутренний бюджетный лимит не считаются ценой договора.
- Поддерживаются TXT и формулировки учебного набора. OCR, PDF/DOCX, электронная подпись, юридическая экспертиза и произвольные корпоративные регламенты не реализованы.
- Это демонстрационный прототип, не юридическое заключение.

## Метрики качества

- **Field Exact Match:** доля точно извлечённых значений суммы и срока относительно размеченного набора.
- **Evidence Coverage:** доля найденных значений с корректной цитатой и ссылкой на исходный абзац. Целевой показатель для отображаемых значений — 100%; фактические показатели нужно получить тестированием.

## PostgreSQL: схема и persistence foundation

В ветке `feat/postgresql-document-model` добавлен первый слой хранения. PostgreSQL предназначен для структурированных метаданных, связей документов, извлечённых фактов, доказательств и истории условий; оригиналы также сохраняются в поле `documents.content` на этапе MVP.

- Схема: `src/database/schema.sql`. Она создаёт ENUM-типы, parties, contracts, documents, document_signatures, document_relations, document_references, evidence, document_facts и contract_conditions.
- Подключение: `src/database/connection.py`. DSN читается из `DATABASE_URL`; подключение ленивое, поэтому текущий in-memory сценарий не требует запущенного PostgreSQL.
- Репозиторий: `src/database/repositories.py`. `PostgresRepository.persist_engine(documents)` сохраняет документы, стороны, извлечённые факты и evidence в одной транзакции, затем связывает письма/допсоглашения с базовым договором.
- Драйвер: psycopg 3.

Пример локальной настройки PostgreSQL:

~~~powershell
$env:DATABASE_URL="postgresql://stereosagent:YOUR_PASSWORD@localhost:5432/stereosagent"
psql $env:DATABASE_URL -v ON_ERROR_STOP=1 -f src/database/schema.sql
~~~

**Важно:** это persistence foundation, а не завершённая миграция приложения. Streamlit и ContractEngine пока продолжают использовать текущий in-memory набор документов; репозиторий ещё не подключён к UI и не выполняет автоматическую загрузку отсутствующих приложений в document_references. Таблица contract_conditions задаёт модель временных условий, но текущий resolver пока остаётся источником юридически применимого snapshot. Перед включением persistence в основной сценарий нужны интеграционные тесты с реальным PostgreSQL, миграции схемы и отдельный workflow для ссылок на отсутствующие приложения.

## Масштабирование до 100 000 документов и ACL

Добавить объектное хранилище оригиналов, PostgreSQL для метаданных/версий/состояний, очередь и независимые workers для обработки, полнотекстовый и при необходимости векторный retrieval. Права доступа проверять до поиска и выдачи фрагментов, а также повторно при формировании ответа. Логи tool calls и решений хранить с tenant/user scope. Kafka/Spark вводить только при подтверждённой потоковой нагрузке и объёмах.

## Оценка достаточности данных (Answerability Assessment)

После tool-calling агент выполняет отдельную проверку достаточности доказательств: структурированный JSON содержит статус answerable/partial/unanswerable, краткий ответ, причину невозможности полного ответа и конкретный список недостающих данных. Проверяющая модель получает исходный вопрос, черновик и трассировку инструментов; черновик не считается доказательством. При отсутствии доказательств или проблемах проверки ответ явно помечается как непроверенный. Важно различать отсутствие значения в тексте, отсутствующее приложение/спецификацию и документ, требующий проверки.

## Генерация вариантов стоимости с подтверждением пользователя

Для запроса вида «предложи стоимость STN-103» Python-маршрут проверяет номер договора и состояние поля суммы. Если цена не определена, отдельный вызов Ollama возвращает три сценария по JSON schema (экономный, базовый, с резервом) с допущениями и рисками. Streamlit показывает варианты для выбора. Выбор не записывает цену в договор, не меняет resolver и не превращает гипотезу в согласованное условие. Бюджетный лимит не используется как цена или якорь. Это candidate generation с human-in-the-loop approval, а не prediction факта.
